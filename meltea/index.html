The recipe

Four pieces, all of them pure.

The Elm architecture in OCaml: a model, messages, a pure update and a pure view in mlx. No hooks and no components with state: an event handler is a message.
counter.mlx
type message = Increment | Decrement | Reset

let update message count =
  match message with Increment -> count + 1 | Decrement -> count - 1 | Reset -> 0

let view count =
  <div className="counter">
    <button onClick=Decrement>(Html.text "-")</button>
    <output>(Html.int count)</output>
    <button onClick=Increment>(Html.text "+")</button>
    <button onClick=Reset disabled=(count = 0)>(Html.text "reset")</button>
  </div>

let () = Option.iter (fun root -> ignore (Program.sandbox ~init:0 ~update ~view root)) root
  1. 1ModelcountAny OCaml value. Immutable, so an unchanged reference is an unchanged value.
  2. 2MessagesIncrement | Decrement | ResetA variant. An event handler is a message, not a closure over state.
  3. 3updateupdate message countA pure function from a message and the model to the next model.
  4. 4viewview countA pure function in mlx, compiled into a template and a refresh.

The counter's view compiles to this JavaScript (names shortened):

counter.js
const template = View.template(Template.html("<div class=\"counter\"><button>-</button>…"),
  (scope, div) => {
    const minus = div.firstChild, output = minus.nextSibling, plus = output.nextSibling, …;
    return [handler_hole(scope, minus, "click"), text_hole({ parent: output, before: null }), …];
  });

const view = (count, dispatch) =>
  View.compiled(template, 2, (scope, holes) => {
    const sent = check(scope, 0, dispatch), counted = check(scope, 1, count); // one === each
    if (sent === Changed) set_handler(holes[0], () => dispatch(Decrement));  // first draw only
    if (counted === Changed) set_text(holes[1], String(count));
    …
  });

Steeped at build time

The compiler reads your update, so you annotate nothing.

No signals and nothing in your code. meltea-ppx finds which message writes which field, and which part of the view reads it.

Fields

The compiler reads update and view: which model fields each message can change, which fields the view reads. A message that changes nothing the view reads does not call it.

Fanout alerts

It follows each frequent event to the message it sends, the fields that message writes and the lists that read them. When typing would make a list check all its rows, it says so at the handler.

Remembered values

A derived let at the top of a view is computed again only when a field it reads changed; otherwise it is the same list, and the holes that read it are skipped.

Served hot

Keep the state while you edit. Render on a server without a DOM.

Hot reload

An edit shows the new view of the old model.

With ~start:Program.hot and Vite's HMR, as elm-watch does. When the module's types changed, it starts from init.

Server rendering

One module, natively or in Node.

Under meltea-ppx -server the same view compiles to code that writes strings, with no DOM. The browser build hydrates the HTML, and clicks and typing made before the code arrives are delivered in order.

dune
(executable                              ; the server, native
 (name server)
 (libraries meltea.server)
 (preprocess (pps meltea-ppx -server)))

(melange.emit                            ; the browser
 (target app)
 (libraries meltea)
 (preprocess (pps melange.ppx meltea-ppx -hydratable)))
